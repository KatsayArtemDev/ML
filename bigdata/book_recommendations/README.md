# Отчет по проекту: Книжные рекомендации

## 1. Первичное исследование данных (EDA)

В ходе первичного анализа исходных данных (`audition.parquet` и `content.parquet`) были выявлены следующие особенности, которые повлияли на дальнейшую очистку:

* Объем и качество данных: Основная таблица `audition` содержит 1 002 896 записей. В ходе проверки обнаружено, что 70% значений в поле `app_version` пропущены - это стоит учитывать, если потребуется аналитика по конкретным версиям приложений.
* Аномалии: Были выявлены технические некорректности:
* Встречаются конфликтующие флаги контента (одновременное наличие `adult_content_flg` и `kids_content_flg` как `True` у 74 725 записей), что требует осторожности при фильтрации.
* Есть редкие случаи с нулевой длительностью или экстремальными значениями, которые были отфильтрованы.


* Фильтрация: Для выполнения анализа был выбран период с 2024-10-01 по 2024-11-30 и регион "Москва, Россия". После очистки от дублей и применения фильтров количество записей составило 80 336. Это надежная выборка, на которой можно строить выводы.

## 2. Анализ предпочтений пользователей

Изучив распределение активностей, можно выделить несколько заметных трендов:

* Популярные платформы: Пользователи чаще всего слушают контент через "Станцию" (6 687 уникальных пользователей). Это основной канал потребления, опережающий мобильные приложения "Букмейт" и "Музыка".
* Жанровые предпочтения: Жанр "Аудио" является безоговорочным лидером (11 221 слушатель). Также востребованы детская литература и классика.
* Типы контента: Аудиокниги доминируют по времени прослушивания и количеству сессий.

Распределение активности по дням недели показало, что пользователи слушают контент довольно равномерно, без резких скачков в выходные, что говорит о привычке регулярного потребления контента в Москве.

## 3. Анализ плана выполнения запроса (user_mart)

Для формирования витрины `user_mart` был проанализирован план выполнения (explain).

* Особенности плана: Основной вклад в стоимость выполнения вносят операции `Join` и `Exchange` (перемешивание данных между нодами). Поскольку `user_mart` требует агрегации большого количества данных из разных источников, Spark выполняет сортировку и группировку на этапе `SortAggregate`.
* Дорогие операции: Наиболее "тяжелым" участком является соединение данных (`SortMergeJoin`) по идентификатору пользователя `puid`. Перемешивание данных по сети для выполнения join - главная статья расходов времени.
* Возможные оптимизации:
* Filter Pushdown: Оптимизацию можно ускорить, если перенести фильтрацию по датам и геолокации (where-clause) максимально "близко" к источнику данных (до проведения JOIN). Это сократит объем данных, передаваемых по сети.
* Broadcast Join: Если бы таблица контента была значительно меньше (например, при фильтрации), можно было бы принудительно использовать `broadcast`, чтобы избежать дорогого shuffle данных.



## 4. Заключение

В процессе реализации ETL-пайплайна были успешно построены пять витрин данных. Реализованный код позволяет гибко настраивать параметры (период, регион, колонки распределения) через аргументы запуска, что делает систему удобной для повторного использования. Данные готовы к передаче в модели рекомендаций.
